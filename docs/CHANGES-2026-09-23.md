# 3D preview prototype — changes, 2026-09-23

## Overview

This adds one new folder, `scripts/3d-test/`, containing an **offline 3D
rendering prototype** for the build preview, plus its findings. It answers a
question the Phase 4 preview work left open in
`specs/05-phase-4-preview.md`: the SVG preview's interiors are flat, and the
spec closed Route B with "if the preview is ever pushed further, the next
thing to try is interior surface character". This is that investigation.

**Nothing in the app changed.** No route, component, `lib/` module, migration
or catalog row is touched. `git diff` against the tracked tree shows `.gitignore`
as the only pre-existing file modified, and that is to *exclude* the
prototype's render output. The prototype does not run at request time, is not
imported anywhere, and every file carries a `TEMPORARY` header.

**Status: a prototype for a decision, not a feature.** It is checked in so the
work can be judged, re-run and either adopted or deleted. It is not wired to
anything and can be removed with `rm -rf scripts/3d-test` plus the `.gitignore`
block, with no other effect.

---

## The question it answers

> Does a procedurally generated 3D case, rendered with real materials and
> light, beat the current facet SVG at the one thing that SVG cannot do —
> continuous surface falloff across an interior?

Short answer, from the first round: **partly, and not enough to replace the
SVG top-down.** The investigation then continued into whether a full
assembled watch could be rendered from catalog data, and how such images
could be served without a GPU per request. `scripts/3d-test/REPORT.md` is the
long-form record, written as the work happened, including the passes that
failed.

---

## What changed, how it works, and why

### 1. Procedural case geometry — `case_geometry.py`

**What.** Pure-numpy geometry built from a part's own stored dimensions
(`attributes.caseDiameterMm`, `lugWidthMm`, `dialApertureMm`): a signed
distance field for the case silhouette, a marching-squares contour extractor,
and a height field.

**How.** The silhouette follows the same construction as `caseOutline()` in
`lib/preview/art/parts.tsx` — the same lug root/tip thickness, 1.75mm lug
overhang, fillet radius and crown-guard shoulder — so a comparison between
the SVG and the render is about rendering, not about two different readings
of the same numbers. The outline is a smooth union of a body circle and four
lug polygons, which gives true fillets instead of hand-placed curves.

**Why.** Because the catalog's numbers are what makes a drawn preview
defensible. Geometry generated from the stated dimensions can be *checked*:
`measure()` reads the built mesh back and compares it to the inputs. It
measures 42.500 / 22.000 / 45.998mm against a stated 42.5 / 22 / 46, within one
grid step (0.04mm), and 37.825 / 19.992 for the 37.8mm set.

**Caveat, recorded honestly.** Only three numbers come from the catalog.
Lug thickness, chamfers, case height, crown guard and the bezel seat are
constants read off photographs — exactly as the production SVG does it.

### 2. Two renderers — `render_case.py`, `render_solid.py`

**What.** `render_case.py` is the first experiment: a top-down height field
of the case alone. `render_solid.py` is the one that matters now: a closed
solid (flanks, lug undersides, spring-bar holes, caseback) plus bezel,
insert, chapter ring, crown, dial, hands, crystal, gasket, day-date wheels and
six strap types — each a separate object, built from the same dimensions.

**How.** Blender 4.5 headless with Cycles. Everything is parameterised by
environment variables (`CASE_FINISH`, `HAND_COLOR`, `STRAP`, `DIAL_TAG`,
`INSERT_TAG`, `RING_TAG`, `LAYER`, `CRYSTAL`, …), so a variant is a different
command, not an edited file.

**Why Blender.** trimesh/pyrender was the cheaper option but has no
anisotropic shading, which would have made "brushed steel" impossible to
test. This was checked before choosing, and is recorded in the report.

**Notable decisions, all with a reason in the report:**

- **Flat crystal removed by default** (`CRYSTAL=none`). At normal glass
  values the studio lights reflected onto the dial as grey discs. Kept as an
  option, with an AR-coated variant, a domed variant and a "studio streak"
  variant, because the choice is aesthetic and belongs to the product owner.
- **Denoiser off.** Cycles' denoiser takes its detail hints from the first
  surface a ray hits. Behind a crystal that is featureless glass, so it
  smoothed the dial print into plastic. Rendering at more samples without the
  denoiser fixed it, at roughly 3x the time per image.
- **Light linking** keeps the key light out of the crystal while it still
  lights the steel.
- **A shading bug worth knowing about:** the crystal's flat faces were
  smooth-shaded into its bevel, which curved the normals across the whole
  face and turned a flat crystal into a lens that visibly bent the hands.
  Fixed by splitting shading at every bevel step.

### 3. Texture generators — `make-insert.ts`, `make-textures.ts`, `pick-dials.ts`

**What.** Generated prints for the bezel insert (60-minute dive scale),
the chapter ring, and the day-date wheels; the vendor dial photo with its
date window cut open; and the dial selection for a render batch.

**How.** SVG composed in code and rasterised with `sharp` (already a
dependency), sized to the parts' *stated* millimetres — insert 38.0 / 31.8,
chapter ring 30.5 / 27.7 — so the print lands at the right scale on the mesh.
The dial's date window is found by flood fill from the 3 o'clock area and its
alpha cleared, which also distinguishes a wide day-date window from a
date-only one.

**Why generated rather than photographed — and this needs a decision.**
Every lumed black SKX-style insert in the catalog with a prepared asset was
photographed with its lume *glowing*, which reads as wrong in a daylight
render. Every chapter-ring asset is a three-quarter perspective photo that
cannot be projected onto a ring seen from above. So these prints are
**approximations of the design, not the vendor's artwork**. The dial is the
only photographed element.

> **Open question for the owner.** These renders mix a real vendor photo (the
> dial) with generated designs (insert, chapter ring, date wheels) that look
> equally real. For a tool whose promise is "never tell someone two parts fit
> when they don't", there should be an explicit rule about showing a generated
> approximation of a real product's printing. The demo pages label it; a
> shipped feature would need a policy.

### 4. The layered pipeline — `LAYER=` mode, `render-batch.sh`, `make-manifest.ts`

**What.** The part that makes this usable without a GPU per request: each
part is rendered **once, on its own**, as a transparent PNG, and the browser
stacks the images.

**How.** In `LAYER=` mode everything except the chosen slot is either hidden
or made a **holdout** — rendered as a hole in the alpha channel. Anything that
can sit in front of a part and whose geometry never changes between options
(case group, insert, chapter ring) is a holdout, so each layer's alpha is
already cut where something in front of it will be drawn. The browser then
composites in a fixed order with no depth information. The hands layer keeps
the dial as a **shadow catcher**, so the hands' shadow travels with them onto
whichever dial is underneath.

**Why.** Rendering every combination is impossible: the visible slots alone
multiply out to roughly 10^18 builds. Rendering per request needs a GPU
server and seconds of latency per click. Layers make part switching an image
swap: measured at **20–40ms**, with the whole batch-1 library at 8.3MB of WebP.

**Two failures worth recording, because they will recur:**

1. **Stacking order.** The strap layer was drawn *below* the case, so the
   case covered it even where the strap is genuinely in front, and the strap
   read as passing underneath rather than plugging into the lugs. Because each
   layer already holds out the case, the strap must be drawn **last**.
   `out/layers.html` has this the right way round and says why.
2. **Parts that light each other cannot be separated.** After the order fix
   the strap was still about 15% too bright at the lugs (measured mean 56 vs
   the full render's 49), because a layer rendered alone never sees the case's
   shadow. Fixed by rendering **case and strap as one layer**
   (`LAYER=casestrap`): the junction then measures 49, identical to the full
   render. The general rule: group the parts that visibly light each other,
   keep everything else separate. The count multiplies only inside a group.

### 5. Two viewer pages — `out/index.html`, `out/layers.html`

**What.** Static pages for judging the work. `index.html` is the record of
the investigation (facet SVG vs 3D vs a vendor photo, crystal options, strap
options, three finished builds, a rotatable glTF). `layers.html` is a working
layered configurator.

**How.** `layers.html` reads `layers/manifest.json` and builds its controls
from it, so a new render batch appears without editing the page. Each option
is labelled with how many catalog listings it stands for.

**Why they live in `out/`.** They reference `layers/…` relatively. They are
the only two files in `out/` that are checked in.

### 6. Type fixes to the prototype's own scripts

**What.** `compare.ts`, `make-textures.ts` and `make-manifest.ts` were made
type-clean.

**Why.** The repo type-checks everything with `strict` and
`noUncheckedIndexedAccess`, and `pnpm check` runs `tsc --noEmit` over the
whole tree. As first written the prototype added 20 type errors and **broke
`pnpm check` for everyone**. The alternative — excluding `scripts/3d-test`
from `tsconfig.json` — was rejected because it weakens a shared setting for
the sake of throwaway code. The fixes are small: tuple return types, an
argument guard, and `?? 0` on raw pixel reads.

### 7. `.gitignore`

Adds `scripts/3d-test/out/*` (with the two viewer pages excepted) and
`__pycache__/`. The render output is about 319MB and is reproducible from the
scripts; six small sample renders are checked in under
`scripts/3d-test/samples/` (377KB total) so the PR can be reviewed without
running Blender.

## Results

| | measured |
|---|---|

| Builds that library covers | 51,840 |

## Trade-offs

- **Layers vs per-build rendering.** Layers are instant and need no server
  GPU, but are locked to the pre-rendered camera angles, and any lighting
  change invalidates the whole library. Per-build rendering is exact and
  unbounded in variety, but needs a GPU service and seconds per image.
  The suggested route is layered for browsing, full render on save/share.
- **The holdout trick assumes fixed occluder geometry.** True within one case
  shape. Each additional case shape needs its own library for the parts behind
  it, so the library grows as parts × case shapes.
- **Generated prints vs vendor photos.** See the open question above.
- **Exaggerated Milanese weave.** Drawn at about 0.9mm; the real weave is
  about 0.3mm, which is below a pixel at this distance. Labelled on the page.

## Behaviour changes, dependencies, setup

- **No runtime behaviour changes.** Nothing imports the prototype.
- **No new npm dependencies.** The scripts use `sharp` and `better-sqlite3`,
  both already dependencies.
- **New external tool, not committed:** Blender 4.5+ (about 400MB) is needed to
  run the renderers. Set `BLENDER` or put `blender` on `PATH`. Nothing in
  `pnpm check`, `pnpm build` or the test suite needs it.
- **No new environment variables** for the app. The prototype's own variables
  are documented in the script headers.

## Known issues and unfinished work

- **Dimensions beyond three numbers are constants.** Case height, lug
  thickness, chamfers and the bezel seat are not catalog-derived.
- **A pre-existing bug found in production art, not fixed here.**
  `CaseBody` in `lib/preview/art/parts.tsx` computes the bezel seat radius
  from `m.insertOuter`, which defaults to 38mm when no insert is chosen —
  whatever the case diameter. On a 37.8mm case the seat is wider than the
  case and the top rim disappears. The prototype clamps the seat inside the
  case; **the SVG still has this.** Left for the owner to decide, since it
  changes production art.
- **One case shape only** (SKX007 family, 278 of 401 approved cases).
- **Hands:** only the sword silhouette of the nine in the vocabulary.
- **Inserts:** dive only; GMT (287 parts) not generated.
- **Crowns:** one knurled shape, and the crown is currently part of the case
  layer rather than its own slot.
- **Bracelet links** are rounded boxes; real jubilee and oyster links are
  curved lozenges, and the result reads slightly "toy" up close.
- **No clasp, spring bars, or movement** (the day-date wheels are the only
  visible part of a movement).
- **Scene rebuild dominates render time.** About 7 of every 12 seconds is
  rebuilding the scene from scratch; batching variants inside one Blender
  session would cut library time by roughly half.

## Suggested next steps

1. Decide the policy question about generated prints before any of this ships.
2. Decide whether to fix the production `seatR` bug.
3. If continuing: remaining hand shapes, then GMT inserts, then crowns as
   their own slot — in that order, by catalog coverage.
4. Batch the renders inside one Blender session before the bigger batches.

## How to verify

**Without Blender** (a minute):

```bash
pnpm check                      # tsc + vitest + verify-catalog, all pass
npx tsx scripts/3d-test/pick-dials.ts     # reads the catalog, writes the dial plan
npx tsx scripts/3d-test/make-insert.ts    # writes out/insert-skx.png
```

Then look at `scripts/3d-test/samples/` for what the renders look like, and
read `scripts/3d-test/REPORT.md` for the reasoning and the failed passes.

**With Blender 4.5+** (about 30 minutes for the full batch):

```bash
export BLENDER=/path/to/blender            # or put blender on PATH
npx tsx scripts/3d-test/pick-dials.ts
TAG=d01 DIAL_ID=<id from the plan> npx tsx scripts/3d-test/make-textures.ts
TAG=ins-black npx tsx scripts/3d-test/make-insert.ts
bash scripts/3d-test/render-batch.sh
npx tsx scripts/3d-test/make-manifest.ts
npx serve scripts/3d-test/out               # then open layers.html
```

A single image, to check the toolchain in about 20 seconds:

```bash
TENT=0.9 FLOOR=0.3 blender -b --factory-startup \
  --python scripts/3d-test/render_solid.py -- D hero /tmp/one.png
```

The render prints a `RESULT` line with the mesh measurements, which is the
geometry check described above.
